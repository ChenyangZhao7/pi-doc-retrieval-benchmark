# 第 5 问：结论与选型建议

> 日期：2026-11-04  
> 依据：core20 的 17 格（S/M 各 3 次、L 各 1 次）、G3/G4、recall、compaction 对照、G4 S 人工复核  
> 边界：20 题试点、10/50/100 份语料；**不是 163 题全量，也不是 2000 份结论**

## 1. 一句话结论

**在 10–100 份、20 题的当前范围内，纯 CLI（G1）已经够用，向量 RAG 没有证明出稳定增益，混合组也没有更划算。**  
如果语料继续变大，最可能先需要 RAG 的是 **B 类语义改写**和 **C 类跨文档汇总**，但当前数据还不足以给出规模拐点。

## 2. 哪类任务用 CLI 就够

| 任务类型 | 当前建议 | 数据依据 | 说明 |
|---|---|---|---|
| A 精确事实 | **CLI 够** | G1 S/M/L = 1.000 / 1.000 / 1.000 | 关键词明确，grep/read 最划算 |
| B 语义改写 | **CLI 够，但优先观察** | G1 B = 1.000 / 0.933 / 1.000；G3 没有更高 | Agent 会自己换词（20% 运行需要 ≥2 种 grep pattern） |
| C 跨文档汇总 | **CLI 够** | G1 C = 0.967 / 1.000 / 1.000 | 多轮 read + 拼接，20 题内稳定 |
| D 开放研究 | **都不够好，CLI 不更差** | G1 D = 0.833 / 0.750 / 0.750；G3/G4 0.667–0.917 | 共同短板是停止条件、长文组织和派生计算 |
| E 无答案 | **CLI 最稳** | G1 E = 1.000；G3/G4 原始 0.667–0.889（主表口径） | 规则会把“拒答+背景数字”判 0.5；人工核对只放附录 |

结论：**默认用 G1；不要默认上 G0 或 G4。** 人工复核：G3/G4 的 S/L 共 78 条，72 条完全一致（92.3%），78 条含 0.5 可接受；说明“RAG 没赢”不是判分器单方面造成的。

## 3. 哪类任务必须上 RAG

在现有数据里，**没有一类被证明“必须”上 RAG**。但有三个明确的“候选条件”：

1. **检索页码命中开始掉**：page@5 从 S 的 1.000 降到 M 的 0.913、L 的 0.830；
2. **B 类在更大语料上变差**：当前 G1 B 仍高，是因为 Agent 会换词；语料越大，换词成本越高；
3. **C 类需要跨很多文档**：当前最多 3 家；到几十家时，grep+read 的轮数和 token 会先出问题。

所以更准确的说法是：

> **RAG 不是“某类题必须”，而是“规模超过某个点后，B/C 会先需要”。这个点当前没有测出来。**

## 4. 混合方案怎么搭最划算

G4（G1 + bash + search_docs）当前没有打赢 G1：dense 3 次为 S 0.958、M 0.942；hybrid 1 次为 S 0.925、M 0.950、L 0.950，仍没有超过 G1 的 0.975 / 0.958 / 0.975。因此不建议把“全工具混合”当默认。

建议的轻量混合：

| 策略 | 做法 | 适用 |
|---|---|---|
| 默认 | G1：read / grep / find / ls | A/B/C/E，10–100 份 |
| 按需检索 | 先 grep；连续 0 命中或同义词多时，再调 `search_docs`（默认 hybrid：dense + BM25） | B 类、术语不一致 |
| 大语料 | search_docs 常开，但 `k=5` 起步，不默认 8–10 | 超过当前 100 份后 |
| 长任务 | 保留 CLI，加停止条件/分段交付；不要靠反复 compaction | D 类 |
| 不建议 | G0 全文注入 | 成本 18 倍且不涨分 |

关键控制项：

- `search_docs` 默认 `k=5`，不要一上来 8–10（当前 Agent 偏向 8–10，token 会上去）；
- 所有结论必须带文件名+页码，否则 evidence_hit 会虚低；
- E 类要明确“未找到”，不要补别家数字；
- D 类要给停止条件，否则单题可到 20 万 token 以上。

## 5. 成本与压缩的结论

- G0：M 档 439k token/次，约 G1 的 18 倍，总分还低 0.008；只在需要“上限参考”时跑；
- G1：S/M/L 都是 24–27k token/次、$0.0019–0.0028/次，是最稳的默认；
- G3：M 档 30.8k token/次，是当前最高的常规组；hybrid 后 M 档 0.900→0.925，但 1 次重复不足以下强结论；
- 正常 700 次运行 **0 次 compaction**；强制压缩 4 个案例，单次省 55%–76% 上下文，3 个案例质量不降；反复压 12 次时耗时 17.6 倍、token 2.2 倍，分数没提高；
- 中文 grep：繁简、全角数字、去千分位、换单位基本 0 命中；Agent 靠换词规避，代价是更多轮次。

## 6. 不能说的话

1. 不能说“CLI 在 2000 份时仍然够用”——只测到 100 份；
2. 不能说“RAG 一定更准”——20 题内 G3/G4 没有稳定超过 G1；
3. 不能说“混合一定更好”——G4 没有打赢 G1；
4. 不能把 E 类原始分当幻觉率——它是规则分；人工核对只作附录，主表仍用原始分；
5. 不能把 G0 的缓存价当通用价——缓存未命中时 M 档约 $0.13/次。

## 7. 一页汇报口径

> 在当前 10–100 份公开年报、20 题试点上，纯 CLI 的 G1 是性价比最高的默认方案（0.958–0.975，24–27k token/次）。G3 向量检索没有稳定增益，G4 混合也没有更划算；G0 成本约 18 倍且不涨分。只有在语料继续变大、B/C 类的检索命中开始下降时，才建议把 search_docs 作为按需工具接入，而不是默认全量 RAG。
