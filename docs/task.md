## 1. 背景与目标

验证「只给 pi 原生 CLI 工具、不建向量库」在中文企业文档上的检索问答与研究总结效果，并与向量 RAG、混合方案做对照。

要回答的 5 个问题不变：

1. **准确性**：分题型看，纯 CLI 检索的答对率和证据命中率跟向量 RAG 比差多少。
2. **成本**：每题的输入/输出 token、工具调用次数、对话轮数、端到端耗时、费用。
3. **规模**：语料从 10 份到 100 份时，指标怎么变；哪个规模开始明显变差。
4. **上下文行为**：长任务里 Agent 怎么挑关键词、怎么换词、读整篇还是分段；是否触发 compaction，压缩后质量掉多少。
5. **结论**：哪类任务用 CLI 就够，哪类必须上 RAG，混合方案怎么搭最划算。

## 6. 实验设计

### 6.1 组别

| 组 | 工具 | 说明 |
|---|---|---|
| G0 | 无 | 语料整篇塞入；L 档因上下文/费用放弃 |
| G1 | read / grep / find / ls | 纯只读 CLI，主实验组 |
| G1+ | G1 + INDEX.md / AGENTS.md | 目录索引，测“廉价地图”的增益 |
| G2 | G1 + bash | 允许管道、rg、wc、awk；专用目录 + guard |
| G3 | read + search_docs | 向量 RAG 对照 |
| G4 | G2 + search_docs | 工具级混合 |
| G3h / G4h | 同上 + hybrid 检索 | dense + BM25（0.9/0.1），1 次重复 |

### 6.2 重复次数

- **主实验：core20 ×3 次**（S/M 主要组）；
- **L 档与 hybrid：core20 ×1 次**；
- 原因：受 Token 用量、费用、硬件和现实时间限制；多次重复不改变结论，只增加成本；
- 报告必须如实标注每个格子的重复次数，不能把 1 次当 3 次，也不能把 L 与 S/M 直接比方差。

### 6.3 运行方式

- 每题独立：`--no-session`，题与题之间不共享上下文；
- 各组同一模型、同一题集、同一段追加提示词、同一超时；
- 只读组关闭 `bash` / `edit` / `write`；
- G2/G4 在专用隔离目录运行。

### 6.4 指标

| 指标 | 计算方式 |
|---|---|
| 答对率 | LLM 对照参考答案打分（0 / 0.5 / 1） |
| 证据命中率 | 回答引用的文件和位置是否包含标注证据 |
| 幻觉率 | 回答里语料中找不到来源的事实、数字占比 |
| E 类拒答率 | 无答案题里如实说“查不到”的比例 |
| Token / 费用 | `usage` 汇总，分 input / output / cacheRead / cacheWrite |
| 工具调用次数 / 轮数 | `tool_execution_start` 按工具名统计；`turn_start` 计数 |
| 端到端耗时 | 脚本计时 + `durationMs` |
| 压缩 | `compaction_end` 次数、`tokensBefore` / `estimatedTokensAfter` |

### 6.5 行为分析

- 每类题挑 3 条典型轨迹，共 15 条，写清搜了什么词、换了几次词、读了哪些文件和段落、在哪一步走偏；
- 中文检索压力测试：繁简、全半角、数字格式（`1.2 亿` vs `120,000,000`、千分位 vs 去逗号）对 grep 的影响；
- 统计真实轨迹中的 grep 命中率、换词比例、引用页码比例。

### 6.6 上下文压缩

- 正常运行记录 `compaction_end`；当前 core20 在 1M 上下文下未触发；
- 强制压缩对照：单独 settings，提高 `compaction.reserveTokens`、下调 `keepRecentTokens`；
- 至少保留 3 个压缩前后质量对照案例，并记录压缩次数、token 变化、耗时。

### 6.7 隔离边界（写清楚）

本机没有 Docker Desktop，WSL2 未确认可用，因此 G2/G4 **不是容器隔离**，实际方案是：

1. 语料复制到 `<isolated-corpus>`、`<isolated-corpus>`、`<isolated-corpus>`，Agent 的 cwd 只在这些目录；
2. `corpus_guard` 拦截 cwd 外路径；
3. `bash_guard` 拦截 `pi-docbench`、shell/python/node、`..`、cwd 外绝对路径、Git Bash 路径、`cd` 越界；
4. 关闭 `edit` / `write`；
5. 事后审计成功越界、拦截、外部引用。

**残余风险**：guard 可被混淆绕过；隔离目录内可写；未限制网络；没有 CPU/内存/进程资源隔离。它是“专用目录 + 启发式防护”，不是安全沙箱。报告必须如实写清，不能写成“容器隔离”。

### 6.8 判分

- A/B/C/E 用 Kimi；D 用 DeepSeek V4 Pro；分歧由 V4 Pro 复核；
- `expected=refuse` 用独立薄层判断“是否拒答 / 是否编造”，不改原 `grade.py`；
- 主表使用原始规则分；E 类“明确拒答 + 背景数字”被规则判 0.5 的情况，人工校正只放附录，不进入主表。

## 9. 评估报告大纲

1. 结论（1 页内）：哪类任务、多大规模用纯 CLI 就够，哪类必须上 RAG，推荐的混合方案。
2. 实验设置：模型及版本、pi 版本、语料概况、题集分布、各组配置。
3. 主结果：分题型 × 分组的答对率与成本对比。
4. 规模曲线：S / M / L 三档下的准确率和 token 成本变化。
5. 行为分析：典型轨迹、失败模式分类、中文对 grep 的影响。
6. 上下文压缩：触发频率、压缩率、压缩前后的质量变化。
7. 局限性：只测了哪些模型和领域、打分器偏差、哪些结论不能外推。

## 10. 局限与不能外推的结论

1. **20 题试点，不是 163 题全量**；分类别 n=5、D=2，类别差异可能是噪声；
2. **L 与 hybrid 只有 1 次重复**，S/M 主要组是 3 次，不能直接比方差；
3. **规模只到 100 份**，不是原任务书的 2000 份，不能回答“2000 份时是否变差”；
4. **只测一个模型** `deepseek/deepseek-flash`；Ollama 4B/7B 是负结果，不能外推到其他模型；
5. **G2/G4 不是容器隔离**，是专用目录 + guard + 事后审计，存在残余风险；
6. **E 类判分偏严**：拒答 + 背景数字会被判 0.5，主表保留原始分，附录给人工校正；
7. **判分器有偏差**：D 类派生计算不稳定，G4 出现过自动高、人工低；
8. **费用含前缀缓存**：G0 的低费用依赖 DeepSeek 缓存命中，缓存 miss 时成本显著上升；
9. **G1 M 有旧任务复用数据**：报告需注明 reused，不能全部当本轮新跑。
